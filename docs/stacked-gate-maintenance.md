# Stacked gate maintenance prerequisites

Protected policy P is the authenticated default-branch source. Actual target B,
child H and their prospective merge M remain comparison data. Protected reuse
activation requires genuine default-branch deployment; an unmerged controller or
parent PR approval cannot publish a substitute trusted result. Recheck P/B/H,
current producer run/attempt/artifact and owner review before and after status
publication. Parent closure, deletion, movement or review withdrawal removes
certification; reopening does not restore an old receipt.

`pull_request_target` runs from the PR's base branch, so a parent stacked on
another parent cannot revoke its children from its own events: that source is not
the default branch and fails the protected pin. Revocation therefore runs from
default-branch contexts and compares recorded evidence with live state: each
success description records the exact target B and policy P it certified. A
`delete` or the `requested` delivery of any `workflow_run` sweeps open PRs
from one PR listing and one paginated GraphQL status inventory (an incomplete
inventory revokes rather than skips) and revokes a current success whose record is missing or malformed, whose
P differs from the default-branch tip, or whose B differs from the live direct
parent head of a unique open chain to the default branch (the default-branch tip for a
default-branch PR). Commit statuses are per SHA, so a stacked PR whose head is shared
with any other open PR is never certified. Parent moves without CI
and closed or deleted parents are therefore revoked by the next such run, not
instantly; label or edit churn on a parent no longer revokes children.

Remote APIs provide no transactional compare-and-swap, so final certification also
requires a fresh live pair/policy check after publication.

Sonar driver source O and workflow integration W are separate real commits. O
contains the driver, strict-verifier adapter, official scanner manifest and tests.
W must select O by a reviewed literal full SHA and source/property bindings; O
cannot embed its own SHA. Root independently freezes the actual W workflow bytes,
selected ref and O binding before dispatch. No caller input selects driver code.
A matching expected-workflow SHA is a drift check, not source review or authority.
No maintenance workflow job is installed by this source preparation.

The later W bootstrap must run before any secret introduction, authenticate the
fixed repository/event/ref/run/attempt/workflow source, and verify clean literal O
source/imports. The driver operates separately from candidate checkouts. Existing
SONAR_TOKEN is confined to the protected permission/settings/scanner phase, never
candidate Make, build scripts, local actions, properties, or workflow code.
Scanner input is source data; its configuration is independently reviewed data
outside that tree. The scanner archive is pinned to SonarSource's official
immutable manifest. Current source preparation has not downloaded or executed it.

A nonempty secret, anonymous authentication validation, public HTTP200, or an
administration read alone does not prove analysis permission. The driver requires
a fixed-project REPORT task read and a separate project administration read with
anonymous-denial controls, joined to the fixed project/organization mapping.
Principal and token class remain unknown. Settings endpoint support is established
only by each necessary owned operation; scoped-token support at another endpoint
is not evidence of set/reset compatibility.

Effective source/test/coverage inventories, quality profiles/gate and trusted
properties must be captured, reviewed and independently bound before configuring
CI analysis. The historical evidence contains only Autoscan and branch regex,
not this complete scope. **Operational scope parity and scan readiness remain
unproven.** Synthetic offline scope hashes in tests are not repository parity.
No exclusions, thresholds, settings, paid entitlement or credentials are invented
to fill that gap.

After both permission reads, preserve the prior regex and setting inheritance.
Add only the required literal branch while Autoscan is still enabled; denial
prevents disabling Autoscan. Drain explicit PENDING and IN_PROGRESS tasks before
submission. Save owned expected writes and unresolved operations before requests;
a lost response or task ID keeps recovery pending. Process cancellation does not
prove server cancellation. Restore inherited settings with reset, stop on external
changes, and restore Autoscan last only after another idle check. Settings reads
and writes are not remote CAS.

Analyze the actual committed B independently as the actual LONG target branch,
then H as the PR with both target and base equal that branch. Never synthesize a
revision or substitute main. A completed scanner/CE task is not certification:
`sonar_maintenance_verify.js` adds the stable exact-parent-baseline guard around
unchanged `queue_me_sonar.js` App12526/check/suite/head/base/time/quality checks,
and certifies only the child analysis whose ID the submission task recorded. Public
pull-request analyses carry no analysis ID, so the protected caller supplies an
authenticated reader (`current_pull_request_analysis`, the PR's single successful
current REPORT task) that must return that ID before and after verification.
Analysis history reads use Sonar's 500-row page limit; a longer history fails closed.
Zero active-or-waived issues, zero hotspots and no ignored gate conditions remain
mandatory. Deployment, actual native/authenticated scanner execution, hosted CI,
Sonar and Codex review clearance are separate pending gates.
